TWO

The database became the runtime

That deployment problem made the next decision for me: move the collector into Postgres. The rest of the talk is what changed when the database stopped being only the thing I queried and became the process running my code. "Weekend project," I said.

What an extension actually is

pgpulse.so       →  $libdir
pgpulse.control  →  extension/
pgpulse--0.2.0.sql

postgresql.conf

shared_preload_libraries = 'pgpulse'

Three files, one config line, and one symbol.

The postmaster dlopens your library at startup, before it forks anything, and calls exactly one symbol. Say this clearly because it explains the whole second half of the talk: your Rust is a cdylib inside the database server's address space, in its process tree, under its crash semantics. There is no sandbox. You panic, that's not a bug report. That's an incident.

pgrx does the C part

pgpulse/Cargo.toml

[lib]
crate-type = ["cdylib"]

[dependencies]
pgrx = "=0.18.0"

pgpulse/src/lib.rs

::pgrx::pg_module_magic!();

/// Return the health status
#[pg_extern]
fn pgpulse_health_status() -> String {
    let snapshot = shared_mem::read_snapshot();
    let health_status = format!("{:?}", snapshot.health_status);
    health_status
}

Write a Rust function, get a real SQL function. pgrx generates the C glue and the DDL.

Without pgrx you are writing C-shaped Rust against raw pg_sys. With it you get: - generated bindings to the whole Postgres API, for pg13 through pg18 - #[pg_extern], which does two things: generates a C-ABI wrapper that unpacks the fcinfo and converts Datums to and from Rust types, and generates the DDL, which comes out as CREATE FUNCTION ... LANGUAGE c AS 'MODULE_PATHNAME', 'pgpulse_health_status_wrapper'. Note that last bit: the SQL function is bound to a *symbol name*. Same idea as dlsym("_PG_init") and .set_function(). Postgres finds your code by name, everywhere. - #[pg_guard], which bridges two incompatible error models. Rust unwinds, Postgres uses setjmp/longjmp. It wraps your function in catch_unwind and re-raises a Rust panic as a Postgres ereport, so a panic never unwinds into C. The generated pg_sys bindings do the mirror image with sigsetjmp, so a Postgres error never longjmps through your Rust frames. #[pg_extern] applies #[pg_guard] for you; you only write it by hand for entry points that aren't SQL functions, like _PG_init and the worker. Why it matters: without it, an out-of-bounds index in one of my functions unwinds into C, which crashes the backend, which makes the postmaster kill every other backend and enter crash recovery. With it, that same bug is one ERROR in one session. - safe wrappers over SPI, LWLocks and background workers - cargo pgrx: init, run, test, package pg_module_magic! emits the ABI fingerprint. Without it Postgres refuses to load the library at all: "incompatible library: missing magic block". Credit it honestly, it does an enormous amount of work. Pin the exact version, the API moves and your whole build sits downstream of it.

How it actually boots

postmaster
reads shared_preload_libraries, dlopens pgpulse.so checks the magic block first, or refuses: "incompatible library"
postmaster
dlsym("_PG_init") and calls it by name. no registration, no manifest
_PG_init
guc::init()  ·  shared_mem::init()  ·  bgw::init() define settings · install the shmem hooks · register the worker
postmaster
sizes shared memory, then allocates it RequestAddinShmemSpace(size_of::<Shared<T>>()) → ShmemInitStruct
fork
the worker is forked, and reloads the library so _PG_init runs again, in the child
worker
dlsym("pgpulse_worker_main"), then the poll loop attach signals · connect to SPI · every 10s forever

All of it before a single client has connected.

This is the whole startup, and it explains three things people usually find surprising. One: why shared_preload_libraries and not just CREATE EXTENSION. Two of the things _PG_init does are only legal in the postmaster before it forks. RequestAddinShmemSpace only has an effect while the postmaster is sizing the segment, and worker registration has to happen before the postmaster starts forking. LOAD it in a session instead and you are far too late: no shared memory, no worker, and no error either. Two: why changing the extension needs a database restart. shared_preload_libraries is postmaster-level. There is no reload path. That is the whole reason my dev loop hurt. Three, and this is the one that bites later: _PG_init runs in *every* process that loads the library, including the worker the postmaster just forked. Say that clearly and let it sit, because assumption two is about exactly this. Also worth noting: CREATE EXTENSION is a completely separate thing. Loading the library is dlopen. CREATE EXTENSION is per-database bookkeeping that creates the SQL functions. The worker runs whether or not anyone ever ran CREATE EXTENSION anywhere.

Four contracts, one loop

The extension is small, but it crosses four PostgreSQL contracts. I will build the loop once from those four pieces. Each one will then have a clear role when we get to the failures.

These are not four unrelated APIs. They are the four steps of the collector loop. GUC: Postgres' own settings system. postgresql.conf, SHOW, reload on SIGHUP. I get eleven settings and zero config parsing. Don't invent a config file. BGW: a process the postmaster forks, supervises and restarts. Shared memory: fixed segment mapped into every backend, guarded by a lightweight lock. SPI: run SQL from inside the server. No client, no socket. The next four slides follow that order, then the diagram puts them together. Keep this tour short; the failures will supply the detail.

GUC

GucRegistry::define_string_guc(

My settings become Postgres settings. SHOW works, pg_settings works, reload works.

Postgres already has a configuration system, so don't invent one. Declare a static, register it in _PG_init, and you're done. What you get free: it shows up in SHOW and in pg_settings, operators configure it exactly the way they configure everything else, and there's no config file of mine to parse, validate or document. GucContext::Sighup is the good part. An operator changes a threshold and reloads the config. No restart, no redeploy, no code change. GucSetting::get() reads the current value each time you call it, so the next poll just picks it up. And the trap, which is coming up in issue four: registration is once, in _PG_init, for the life of the process. I had guc::init() in my SIGHUP branch, which feels right and is wrong.

pgpulse/src/bgw.rs · pgpulse_worker_main(), the entry point above

pub extern "C-unwind" fn pgpulse_worker_main(_arg: pg_sys::Datum) {
    BackgroundWorker::attach_signal_handlers(SignalWakeFlags::SIGHUP | SignalWakeFlags::SIGTERM);
    BackgroundWorker::connect_worker_to_spi(Some("postgres"), None);

    loop {
        let interval = Duration::from_secs(guc::POLL_INTERVAL_SECONDS.get() as u64);
        let alive = BackgroundWorker::wait_latch(Some(interval));   // sleep 10s
        if !alive {
            break;                                                  // SIGTERM, or postmaster died
        }
        …                                                           // collect, then write
    }
}
Registered in _PG_init. Postmaster forks it and supervises it. wait_latch, not thread::sleep. A sleeping worker ignores shutdown and hangs your restart. Returns false on SIGTERM or postmaster death. set_function takes a symbol name as a *string*. Remember that, it bites later.

Shared memory

pgpulse/src/shared_mem.rs

static PGPULSE_METRICS: PgLwLock<MetricSnapshot> = unsafe { PgLwLock::new(c"pgpulse_metrics") };

pub fn write_snapshot(snapshot: MetricSnapshot) {   // the worker, every 10s
    let mut guard = PGPULSE_METRICS.exclusive();
    *guard = snapshot;
}

pub fn read_snapshot() -> MetricSnapshot {          // any user session, via SQL
    let guard = PGPULSE_METRICS.share();
    guard.clone()
}

One writer, many readers, one lock. The only state the extension keeps.

One writer every ten seconds, many readers via SQL functions. Only the latest snapshot. No history table, no writes to anyone's database. Prometheus already stores time series better than I will. That's what makes it cheap enough for a production primary. About 10 KB.

SPI

pgpulse/src/collectors/replication.rs · collect_replication_clients()

SELECT
    application_name,
    state,
    EXTRACT(EPOCH FROM replay_lag)::float8  AS replay_lag_seconds,

Spi::connect(|client| {

The primary's own view of every connected replica, read without a connection.

Run SQL from inside the server. No connection, no socket, no auth. The COALESCE matters: replay_lsn is null until the replica reports, so fall back to flush, then write. Otherwise your lag metric is null exactly when you need it. Two numbers, opposite ends of the cluster. Bytes on the primary: how much work is outstanding. Seconds on the replica: how wrong your read is, and null when idle, which looks exactly like broken. SPI has one prerequisite. We'll get there.

This is the complete poll, in execution order. First, SPI asks the primary for pg_stat_replication. That gives one byte gap per connected replica: how much WAL the primary has generated that each replica has not replayed yet. It is local, cheap and available without another connection. But byte gap is workload-dependent. Ten megabytes could mean milliseconds on a busy system or a long time on a quiet one. The product question was "how wrong can this read be?" Only a replica can answer that. So the same worker opens one outbound raw-libpq connection to the configured replica and asks for now() minus pg_last_xact_replay_timestamp(). That gives replay age in seconds. The connection has a five-second timeout; failure returns None instead of blocking the entire collector. Only after that libpq call returns does evaluate_health run over the combined snapshot. No connected replicas is Warning. Otherwise any critical signal returns Critical, any warning signal makes the result Warning, and only a clean snapshot is Healthy. Those numbers on screen are the default GUC values, not constants in the evaluator. Be precise about missing replica time: None does not itself make health worse. The evaluator still uses every primary-side byte gap it has. That is graceful degradation, but it also means collected_at and the logs are still needed to distinguish unavailable data from a genuinely healthy time signal. Finally collect_and_store_metrics returns the completed MetricSnapshot. Only then does the outer worker loop call write_snapshot. There is no partial snapshot in shared memory while libpq is running: readers keep seeing the previous complete snapshot until the new data and health verdict are ready. SQL functions expose that snapshot. The exporter is now only a normal client that reads those functions and translates them to Prometheus. This slide also sets up the failures: the snapshot crosses a shared-memory boundary, SPI crosses a backend-state boundary, and libpq crosses the fork-safety boundary.
FOUR

Three normal Rust assumptions broke

Slow down, this is the fun part and it's why people came. The architecture was coherent. My assumptions were not. I had brought three habits from a normal Rust service: values can own heap data, a process running SQL behaves like a backend, and a synchronous client library is safe to call. Each one crossed a boundary in that diagram. Each one was wrong here.

Assumption 1

Shared memory vs the heap

What I wrote

pgpulse/src/models.rs

pub struct MetricSnapshot {
  pub replication_metrics: ReplicationMetrics,
  pub primary_metrics: PrimaryMetrics,               // holds a Vec<ReplicationClient>
  pub health_status: HealthStatus,
  pub collected_at: DateTime<Utc>,
  pub long_running_queries: Vec<LongRunningQueries>,
}

unsafe impl pgrx::PGRXSharedMemory for MetricSnapshot {}
A Vec is three words: pointer, length, capacity. Twenty-four bytes, sat wherever you put them. The elements are somewhere else entirely, on the heap of whichever process allocated them. Shared memory is one fixed segment mapped into every backend. Different process, different heap. So those twenty-four bytes copy across perfectly. That is the whole problem. Nothing complains, because structurally it is fine. The pointer inside them just refers to an address that means nothing in the process doing the reading.

What happened

postgres=# SELECT pgpulse_collected_at();   -- extension loaded, worker registered
 pgpulse_collected_at
----------------------
                  0        <- forever. no error, no crash, no log line.

The fix

pgpulse/src/models.rs

+use heapless;

-    pub application_name: String,
-    pub replay_lsn: Option<String>,
+    pub application_name: heapless::String<64>,

-    pub long_running_queries: Vec<LongRunningQueries>,

Tests passed. Extension loaded. Postgres said so. Worker registered. And collected_at returned zero. Forever. No error, no log line, no crash. Point at the diff. The unsafe marker did not change; my promise stayed the same. What had to change was the representation behind that promise: a normal Vec became a fixed-capacity heapless Vec whose elements live inline in the shared struct. Ask them: what would you check? THEN THE FIX, same slide: every heap-backed type in the model, replaced. heapless stores elements inline, so the size is known at compile time and no allocator is involved. Note collected_at too: a chrono DateTime became a plain i64, same reason. Honest trade: 16 is a hard cap now. The seventeenth replica gets a warning and a shrug. And close it in a sentence: that unsafe impl was me promising the compiler the struct was self-contained, and I was wrong. Nothing checks it.

set_restart_time of ten seconds, faithfully resurrecting a process that died instantly. Point at the wrapper. The collector call is not the important change. You are a C library, not a crate

.set_function("pgpulse_worker_main")   // Postgres will dlsym this string

pgpulse/src/lib.rs · _PG_init()

// `MyBgworkerEntry` is non-NULL inside every forked BGW process and NULL elsewhere.
extern "C" {
  static MyBgworkerEntry: *const pgrx::pg_sys::BackgroundWorker;
}
let in_bgw = !unsafe { MyBgworkerEntry }.is_null();
if !in_bgw {
  bgw::init();
}

It calls you by name, and it runs _PG_init() again in the worker.

Both of these come from one fact: you are a C shared library, not a Rust crate. First: set_function takes a *string*. Rust mangles symbol names by default, so without no_mangle the symbol in the .so isn't called pgpulse_worker_main, and the postmaster cannot find your entry point. I didn't have this initially. Second: _PG_init runs in every process that loads the library, including the worker the postmaster just forked. So the worker registers another worker. MyBgworkerEntry is a C global that's NULL in the postmaster and non-NULL inside a BGW, and it's what Postgres itself uses to answer this question. Note that GUC and shared memory init still run in the worker, because pg_shmem_init *attaches* to the existing segment there rather than allocating a new one. Only the worker registration is postmaster-only. HONESTY: I had a guard before this, using IsBackgroundWorker, and it never fired. I observed that, I didn't prove why.

That None shipped. For two weeks.

I needed one outbound connection to ask the replica how stale it is. Obvious move: the client library I already used in v1. That's the `postgres` crate, the blocking one, which is a synchronous wrapper over tokio-postgres and stands up a tokio runtime underneath. So "sync API" does not mean "no threads". The diff shows the replacement: remove the postgres client path, bind to libpq through pq-sys, open the connection with PQconnectdb, execute with PQexec, then clean it up. This is still unsafe FFI, but there is no runtime or helper thread hidden underneath it. The reason is simpler than it looks, and it is the surprising bit for a Rust room: a Postgres backend is single-threaded by contract. Memory contexts, the setjmp/longjmp error handling, signal handling, resource owners: none of it is thread-safe. pgrx does not just document that, it enforces it. Every call into Postgres runs a thread check first, and its own source says "It's UB to call into Postgres functions from multiple threads... this is called from inside the setjmp shim, as that code is definitely unsound to call in the presence of multiple threads." Call it off the main thread and you get "postgres FFI may not be called from multiple threads." So the rule is: no runtime, no thread pool, and no crate that quietly starts one for you. That rules out more of crates.io than people expect. Anything with a background thread, a lazy global, or a connection pool. HONESTY: I did not root-cause a specific crash here. I read my own comment, understood the constraint, and removed the dependency. If someone asks what exactly went wrong, say that. Do NOT claim this was fork-safety and inherited mutexes. The postmaster is single-threaded, so there is no second thread holding a lock at fork time. That explanation is real in general and wrong here, and someone will know. THEN THE FIX, same slide: Look at what's being deleted: commented-out tokio, and a function that just returned None. For two weeks that metric was a stub, because a missing metric beats a crashing worker. I'd defend that. It kept the worker alive and honest about what it didn't know. Then raw libpq: synchronous, single threaded, fork safe, already linked in. Null check every pointer, clean up on every branch. Least Rust-feeling code in the project.

An interval is months:i32, days:i32, microseconds:i64, validated on construction. Something in that construction rejected the value. The lesson holds anyway: don't construct a type you only wanted in order to compare it. 2. heapless::Vec is an array with a length, not a list. I wrote clients[count] = rc, which is how you fill a preallocated array in C. Index-assign only writes slots that already exist, and a fresh Vec has len 0 even though capacity is 16. I had guc::init() inside the "config was reloaded" branch. Felt right, is wrong. On reload there is genuinely nothing to do. pgrx reads the new value through the GucSetting next time you call get(). 4. connect_timeout=5. libpq's default connect timeout is effectively minutes. What does not exist is narrative documentation. No guide, no tutorial, no book. And the project used to be called pgx, so a lot of what you find by searching is pgx-era material under the old name. So most of my questions ended in ~/.cargo/registry, reading the source. The examples/ directory in the repo was more useful than anything else. The maintainer streamed pgx development on Twitch years ago and those videos are genuinely still useful. FOSDEM is a large open-source conference; I found slides from a 2025 pgrx talk there. The pattern across those sources was that BGWs, GUCs, SPI and LWLocks are PostgreSQL concepts that pgrx wraps. That explains the three failures we just saw: all three were mistakes about the host, not Rust syntax. Frame it as opportunity, not complaint. The ecosystem is small enough that writing down what you learned is a real contribution. That's why I wrote the blog posts, and it's most of why I'm standing here.

Ready answers: • cost on a primary: two SPI queries and one libpq round trip per 10s, ~10 KB shared memory, no writes. Not benchmarked. • worker crashes: postmaster restarts it after 10s, collected_at goes stale. • why not pgwatch / postgres_exporter: they publish raw numbers, this computes one verdict next to the data. And it was a learning project. • RDS/Aurora: no, no filesystem access. • versions: pg13 to pg18 feature flags, built and tested on 18. Compiled per major version. • testing: cargo test for the evaluator, cargo pgrx test in-DB, docker compose end to end.
